## 系統範圍

| 討論問題 | 最終決策 |
| --- | --- |
| 第一版做哪些事？ | 38 會所的本地調查、名單管理、活動與用餐統計、大會系統匯入準備。填寫本系統不等於完成大會正式報名。 |
| 住宿接待是否納入？ | 第一版不納入住宿接待家庭登記、分配與追蹤。 |
| 誰填寫？ | 與會者自行填寫，或由任何弟兄姊妹協助填寫；不區分或記錄代填者。 |
| 一筆登記代表幾人？ | 一人一筆。 |
| 技術架構與資料庫？ | 頁面沿用參考專案的純 HTML、原生 JavaScript 與靜態部署方式；runtime 不使用 build step。建立本案專用的 Supabase Cloud 開發／測試專案與正式專案，不共用參考專案的資料與權限。 |
| 本機開發如何連 Supabase？ | 沿用參考專案的操作方式：本機靜態伺服器直接連遠端 Supabase Cloud；不使用 local Supabase。開發／測試與正式資料必須分屬不同專案。 |
| 資料庫變更如何管理？ | Schema、RLS、RPC、seed 與 Edge Functions 以 migration／版本化檔案進版控；可用 Supabase CLI 時由 CLI 套用，公司主機無法使用時在 Dashboard 依序執行版控 SQL 與 Edge Function 原始碼，記錄已套用版本，不人工重寫 schema。 |
| Node.js 與 npm 用在哪裡？ | 用於本機靜態伺服器與 Playwright 等開發工具；可用 Supabase CLI 時也用於部署。正式 GitHub Pages 不執行 Node.js server。使用仍受支援且已修補的 Node.js LTS，套件鎖定精確版本並提交 `package-lock.json`。 |
| 要收費或追蹤付款嗎？ | 第一版只統計用餐意願及依目前價格計算的預估金額，不記錄收款、退款或結算。 |

## 與會者資料、登記與修改

| 討論問題 | 最終決策 |
| --- | --- |
| 填哪些個人欄位？ | 姓名必填；會所固定為 38 會所；區從林森、忠孝、杭州選擇。第一版不收可聯絡電話或與會者 email。 |
| 區選項能調整嗎？ | 初始為上述三區，管理員日後可調整；不讓填寫者自由輸入區名。 |
| 首次送出時如何選活動？ | 對當時所有公開開放的活動，逐項明確選「參加」或「不參加」；可以全部選「不參加」。 |
| 後來新增的活動如何算？ | 舊登記對新活動是「未回覆」，不能算成「不參加」。舊登記只查看時可維持未回覆；再次儲存修改或恢復時，必須回答當下所有公開活動。 |
| 同名同區能否登記？ | 可以；系統標示「可能重複」，由服事者確認，不自動擋下或合併。 |
| 已登記的人如何自行查看與修改？ | 回登記頁輸入隨機查詢碼，進入自己的資料頁並按修改；不使用專屬修改連結。姓名、區及流水號不能單獨取得資料或修改權限。 |
| 流水號與查詢碼的關係？ | 每人有固定、易讀的流水號，例如 `38-0001`，供內部核對名單及重設查詢碼；填寫者畫面與公開 API 不顯示流水號。隨機查詢碼負責公開查詢與修改授權；重設查詢碼不改流水號。 |
| 查詢碼格式？ | 使用 8 字元的小寫英數碼，排除容易混淆的 `0`、`o`、`1`、`i`、`l`。輸入時自動轉小寫並忽略空白。舊 5 碼立即失效；查詢碼須唯一且只保存雜湊值。 |
| 查詢碼如何交付？ | 完成登記後只顯示查詢碼，提供複製按鈕及明確保存提醒。建立成功後以 `sessionStorage` 傳至 `success.html`，不得放在 URL；關閉分頁後消失。使用者尚未確認已保存時，離開頁面須提醒。查詢碼只在建立或重設時顯示，資料庫不保存可直接讀出的原碼。 |
| 查詢碼遺失怎麼辦？ | 11/8 上線版先提供部署維護者專用的安全重設指令：輸入流水號、產生新碼、使舊碼失效並寫入 audit。指令從本機安全讀取 secret。完整服事者後台完成後，再由服事者以姓名、區等資料找出紀錄並透過既有實體聯繫方式確認當事人。 |
| 未設定截止時間時能否登記？ | `is_registration_open` 必須為 `true`。截止時間為空代表無期限；有設定截止時間時才檢查是否已截止。 |
| 截止後能做什麼？ | 超過已設定的本地調查截止時間後，停止公開新增與修改；查詢碼仍可查看紀錄。服事者日後可在後台補登與修正。 |
| 能取消與恢復嗎？ | 截止前持查詢碼可自行取消，也可自行恢復。截止後恢復須由服事者處理。取消紀錄保留，但不計入有效人數與費用。 |
| 公開表單如何防濫用？ | 公開新增、查詢、修改經 Supabase Edge Function；服務端驗證查詢碼。建立表單加入 honeypot、最短合理填寫時間與 `create_request_id`；錯誤查詢回傳一致訊息，並保留全站異常門檻及緊急關閉入口。第一版不保存 IP 或 IP 雜湊。 |
| 是否使用 Cloudflare Turnstile？ | 已選 Cloudflare Turnstile 並保留整合接口，但為配合 11/8 時程，正式開放時暫不啟用；後續遇到濫用或時程允許時再設定正式 widget 與服務端 Siteverify。 |

| 管理員新增活動填什麼？ | 活動類型選「聚會、用餐、其他」；可填名稱、時間、地點、說明及選填的每人費用。 |
| 尚未確定的活動如何處理？ | 管理員可調整活動內容與公開狀態；青年大會時間／地點、主日晚間愛筵是否舉行，仍須標示待確認。測試環境可暫時公開用餐及愛筵活動供填寫測試，正式環境不因此自動公開。 |
| 有人選過的活動能刪除嗎？ | 不能硬刪，只能停用並保留既有選擇；完全沒有登記選擇的活動才可刪除。 |
| 費用改了怎麼計算？ | 用最新費用重算目前預估金額；不保存每次調價前的舊金額。 |

| 誰能改詳細時間表？ | 管理員可在後台編輯；調整單堂時間不會新增報名活動。 |

## 角色、帳號與密碼

| 討論問題 | 最終決策 |
| --- | --- |
| 有哪些後台角色？ | 管理員 `admin` 與服事者 `staff`；兩者都能查看全體名單，不按區隔離。 |
| 服事者可以做什麼？ | 查找、補登、修改、取消登記，處理疑似重複，重設查詢碼，更新匯入狀態，查看統計與匯出 CSV。 |
| 管理員另外做什麼？ | 管理帳號、區選項、活動、詳細時間表、截止時間與系統設定。 |
| 誰建立服事者帳號？ | **最終改為管理員在後台建立**，不開放服事者自行申請。第一位管理員由部署者在 Supabase Dashboard／受控初始化流程建立。 |
| 後台用哪種登入方式？ | 畫面使用「帳號／密碼」。參考專案以帳號對應 Supabase Auth 的內部識別；新專案可沿用此操作體驗，實際識別格式須先驗證。 |
| 初始密碼與忘記密碼怎麼處理？ | 管理員建帳或重設時，系統產生只顯示一次的初始密碼並私下交付；服事者首次登入須改密碼。管理員不能查看舊密碼。 |
| 需要 Mailgun、Resend 或寄信網域嗎？ | 第一版不需要。取消自行申請、email 驗證、申請通知及 email 重設密碼流程後，沒有必須寄出的信件。 |

後台權限必須在 Supabase RLS 與 Edge Function 檢查；角色與操作權限依本系統需求重新設定。

11/8 上線前不完成整套後台帳號、名單與設定頁；查詢碼遺失先由部署維護者使用安全指令處理。完整後台列為上線後項目。

## 權限、交易與稽核

| 討論問題 | 最終決策 |
| --- | --- |
| 需要一致更新多張表或狀態時如何處理？ | 建立、修改、取消、恢復及匯入狀態變更須經受控 RPC／Edge Function，並在資料庫交易中完成；後台不得以多次無交易的直接資料表更新取代。 |

| 誰能查看 Audit？ | 僅 `admin` 可查看。第一階段先完成資料與權限，查看畫面延後。 |

## 名單、匯入進度與匯出

| 討論問題 | 最終決策 |
| --- | --- |
| 「報名狀態」追蹤什麼？ | 追蹤 38 會所把本地資料送進大會另一套系統的**內部作業進度**，不代表大會已核准報名。 |
| 匯入狀態有哪些？ | 新登記為「待匯入」；服事者確認後手動設「已匯入」；匯入後資料變動則為「需重新匯入」。按下 CSV 匯出不自動標成已匯入。 |
| 哪些異動要重新匯入？ | 已匯入後，姓名、區、活動選擇變動；管理員變更已參加活動的名稱、時間或開放狀態；已匯入者取消／恢復，也要提示服事者處理大會系統資料。單純調整本地預估費用不影響匯入狀態。 |
| 新增活動會讓所有人變成需重新匯入嗎？ | 不會；舊登記先維持原狀態與「未回覆」，補選後才判斷。 |
| 確認重複時怎麼辦？ | 留下正確的一筆，另一筆標「重複作廢」；若確定是不同人，可標「已確認非重複」。不自動合併或永久刪除。 |
| 取消與重複作廢如何統計？ | 後台保留紀錄供查核，不列入有效人數、預估費用與有效名單。需要同步撤回大會資料的取消紀錄，仍要出現在服事者待辦。 |
| 後台需要哪些統計？ | 依區及活動顯示參加／不參加／未回覆人數、匯入狀態人數，以及目前預估總額。 |
| 第一版 CSV 格式？ | 每人一列、每個目前公開活動一欄，另含姓名、區、流水號、內部匯入狀態；活動欄區分參加／不參加／未回覆。查詢碼不匯出。 |
| CSV 能直接匯入大會系統嗎？ | 目前不能保證。專案內沒有大會系統匯入範本；第一版先提供通用 CSV，取得範本後再對應欄位。 |
| 活動後如何清除個人資料？ | 匯入與核對完成後，由管理員先匯出備份，再手動清除姓名與登記資料。清除日期由 38 會所決定，不先設定自動期限。 |
